# PanoSplit Audit — 2026-07-19

Scope: full read of `index.html` (2,090 lines after fixes), vendored `three.min.js` / `jszip.min.js` (not audited line-by-line; standard minified releases), README. Math verified by hand and by in-browser headless checks (template layout, auto-fit canvas, export crop ratios, degenerate clamping). No commits, no pushes made; local main remains 1 commit ahead of origin, untouched.

## 1. Executive summary

PanoSplit is in good shape for its size. The core model — a single DPI source of truth (`panoImg.width / panoCanvasW`), template layout in image pixels, ratio-enforced export crops — is correct and internally consistent. A prior bug-sweep (already committed locally) fixed GPU texture disposal and rebuild throttling. This audit found **no errors in the split/layout/export math**. What it did find: a data-loss drag-and-drop hazard, a handful of robustness gaps around browser limits and WebGL failure, one consistency bug in free-mode frame creation, and several small UX/persistence nits. **12 fixes applied**, all verified. Feature-sized work (color profiles, huge-image performance, mobile layout, printable hanging guide) is deferred with sketches below.

## 2. Findings, ranked by severity

### High

- **H1 — FIXED. Dropping a file outside the dropzone navigated the page away, losing all work.**
  After the first upload the dropzone is hidden; a drag-drop onto the main app hit the browser default (navigate to file). No window-level `dragover`/`drop` guard existed. Now a window-level handler prevents navigation *and* loads the dropped image anywhere (`index.html:562-570`).

- **H2 — FIXED. Silent/hung export when a crop exceeds browser canvas limits.**
  `canvas.toBlob` returns `null` for oversized canvases (limits vary: Chrome ~268 MP area, Safari much lower). The old code passed `null` into `zip.file(...)` and had no `.catch` on `generateAsync` — a hung "Preparing ZIP…" toast at best. Now null blobs are counted, the user is told how many prints failed and why, and ZIP errors surface as a toast (`index.html:1842-1852`). A tiled/downscale fallback would be the full fix — deferred (D2).

- **H3 — FIXED. WebGL failure killed the whole app.**
  `initThree()` throwing (blocked WebGL, remote desktop, old GPU) aborted the init chain *after* `initEditor()` but *before* `applyPrintSizeToFrames()`, leaving a blank editor with no frames. Now wrapped in try/catch; the app degrades to a fully functional 2D editor + export with "3D UNAVAILABLE" shown (`index.html:589-599`, plus null guards at `index.html:1296`, `index.html:1660`).

### Medium

- **M1 — FIXED. Free-mode "+ Add" created frames with fabricated physical size.**
  `printW` was hardcoded to 16" regardless of crop pixels, breaking the DPI-consistency rule every other path follows — 3D preview scale and the per-frame DPI readout were wrong for added frames (export was still correct, since export derives from crop pixels + ratio). Now derived from `crop px / panoDPI()` like templates (`index.html:772-778`).

- **M2 — FIXED. `clampF` never bounded crop w/h to the image.**
  Degenerate cases (manually shrinking canvas width after choosing a big print) could produce crops taller than the image → sampling outside the bitmap → black bands in the editor and potential ratio-breaking clamps at export. Now w/h are clamped to image dimensions (`index.html:746`). Verified with a synthetic degenerate pyramid layout — all crops stay in bounds.

- **M3 — FIXED. Upload box advertised "click" but wasn't clickable.**
  Only the inner button opened the picker. The whole box is now clickable (button excluded to avoid double-open) (`index.html:557-560`).

- **M4 — FIXED. Re-selecting the same file did nothing.**
  `<input type=file>` change never fires for the same path; value is now reset after each selection (`index.html:554`).

- **M5 — Deferred. Wrap-mode export is asymmetric near image edges.**
  `outerCrop` (`index.html:945`) clamps wrap margins at image borders; the export then enforces the (printW+2d):(printH+2d) ratio against the clamped width (`index.html:1803-1811`), so a crop near an edge gets its face off-center in the output — the printer would fold unevenly. Correct behavior would be to either warn ("crop too close to edge for full wrap") or mirror-pad the missing margin. Sketch in §4.

- **M6 — Deferred. No color-profile handling.**
  Canvas decode flattens to sRGB and `toBlob` emits untagged JPEG. Fine for sRGB sources; Adobe RGB / Display P3 panoramas will shift on a color-managed print pipeline. Practical mitigation: note in the UI/README that output is sRGB; real fix needs an ICC-aware encoder (e.g. embed the sRGB profile with a small JPEG post-processor).

### Low

- **L1 — FIXED. Zero-dimension images (e.g. SVG without intrinsic size) produced Infinity scales.** Guarded in `loadFile` (`index.html:578`).
- **L2 — FIXED. Status bar kept stale DPI + warning banner after removing the last frame** (`index.html:1197-1201`).
- **L3 — FIXED. Escape didn't close the help overlay** (`index.html:1882`).
- **L4 — FIXED. Selecting "Custom" print size wasn't persisted until a size was typed** (`index.html:879`).
- **L5 — FIXED. Dead variable `g=gapPxVal()` in `applyTemplate`** (shadowed by `g2`).
- **L6 — Deferred. `tapeColor()` returns `text`/`bg`/`textCol` fields nothing reads** (`index.html:~1368`). Harmless dead weight.
- **L7 — Deferred. Typed W/H in the print list bypass standard-size snapping** while corner-drag snaps — inconsistent when "Standard sizes only" is ON.
- **L8 — Deferred. Auto-fit clobbers a manually set canvas width.** `applyPrintSizeToFrames` (`index.html:904`) recomputes `panoCanvasW` whenever print size, count, or gap changes — a user who pressed "20ft" then nudges the gap loses their width. Arguably intended ("fit as large as possible"), but worth a "lock canvas width" toggle.
- **L9 — Deferred. In free mode, changing default print size or re-uploading overwrites every frame's individual printW/H** (`applyPrintSizeToFrames` free branch).
- **L10 — Deferred. Editor redraws the full-resolution image every pointermove.** Fine to ~50 MP; a 200–300 MP pano will stutter and cost >1 GB decoded RAM. Mitigation: cache a display-resolution `createImageBitmap` for the editor and keep the full-res image only for texture/export sampling.
- **L11 — Deferred. Mobile layout unusable** (fixed 250 px sidebar, `overflow:hidden` body). Desktop-first is a fair choice for a print tool; a stacked media-query layout would still help tablets.
- **L12 — Note. EXIF orientation is handled implicitly** — modern browsers apply `image-orientation: from-image` to `<img>` decode, and every `drawImage` uses the oriented bitmap. No action needed for current browsers.

## 3. Fixed vs deferred

**Fixed this audit (12):** H1, H2, H3, M1, M2, M3, M4, L1, L2, L3, L4, L5.
**Verified by:** in-browser script parse + function-presence check; unit spot-checks (`snapToStdSize`, `panoDPI`, `clampF` bounds); headless pipeline run (4800×1200 synthetic pano → auto-fit 80" canvas @ 60 DPI, three exact 10×20" non-overlapping crops, ratio-exact in-bounds export crop; degenerate pyramid layout stays in bounds).

## 4. Recommended next steps

1. **Wrap-edge safety (M5):** in `downloadFrames` wrap branch, detect when `outerCrop` was clamped (`oc.w < f.w + 2*wrapPxVal()` etc.) and either mirror-pad the missing side onto the export canvas (`ctx.scale(-1,1)` draw of the edge strip) or badge the frame "wrap incomplete — move crop away from edge" in the editor.
2. **Huge-pano resilience (H2 follow-up / L10):** on load, if `width*height > ~180 MP`, build a display proxy via `createImageBitmap(img, {resizeWidth: 8192})` for editor/3D textures; keep full-res only for export. On export, if a crop exceeds ~16k px on a side, downscale to the DPI actually needed (crop px per inch rarely needs to exceed 300) — this also shrinks ZIP sizes with no print-quality loss.
3. **Printable hanging guide:** the tape-measure view already computes nail positions, drops, gaps, and floor height. Render the same data to a 2D canvas as a letter-size PNG/PDF ("hang sheet") included in the ZIP — highest-value small feature for the actual end task of putting prints on a wall.
4. **Project save/load:** settings persist but the layout doesn't. Serialize `frames` + `panoCanvasW` + image fingerprint (name/size) to a JSON sidecar (download + drag-back-in). Cheap, removes the "browser refresh loses an hour of nudging" risk.
5. **Canvas-width lock toggle (L8)** and free-mode size preservation (L9) — two small state guards.
6. **Batch/overlap features** if ever needed: batch = queue of files reusing current template (loop `loadFile` → `downloadFrames` per file into one ZIP); tile overlap/bleed = per-frame `bleedIn` added symmetrically in the export crop, labeled in the filename (`_+0.25in-bleed`). Both fit the existing architecture without refactoring.
